Broadcast: Discover, Request (always)

Located at the end of the DHCP packet.

Option 1 → Subnet Mask

Option 6 → DNS Server(s)

🧩 What is SAI (Switch Abstraction Interface)?
SAI is an open standard API defined by the Open Compute Project (OCP).
It acts as a hardware abstraction layer between SONiC’s control plane software and the switch ASIC (hardware).

⚙️ Why SAI is Needed
Every switch ASIC vendor (Broadcom, Mellanox, Intel, etc.) has its own proprietary SDK.

Without SAI, NOS developers would need to write different code for every ASIC.

SAI standardizes the interface, so SONiC can run on any vendor hardware without changing upper layers.

🏗 SAI Architecture in SONiC
            High-Level Control Plane
        (teamd, bgpd, orchagent, etc.)
                        │
                 SONiC Redis DBs
                        │
                  orchagent (swss)
                        │
            ┌─────── SAI API (Standard) ────────┐
                        │
              Vendor SAI Implementation (.so)
                        │
                      ASIC
Key components:

orchagent (in swss container)

Reads configuration/state from Redis databases

Translates them into SAI API calls

syncd (also in swss container)

Loads the vendor-provided SAI shared library (libsai.so)

Executes the SAI API calls to program the hardware

SAI library

Vendor-specific implementation of the SAI standard

Talks directly to the ASIC SDK

📌 SAI Object Model
SAI is object-based.

Defines standardized objects like:

SAI_PORT, SAI_ROUTER_INTERFACE, SAI_ROUTE_ENTRY, SAI_NEIGHBOR_ENTRY, etc.

Each object has:

Attributes (properties you can set/get)

APIs for create, set, get, and remove

Example:

To add a route, orchagent creates a SAI_ROUTE_ENTRY object with destination prefix and next-hop.

💡 Key Benefits
Hardware independence: SONiC code doesn’t change across vendors

Vendor flexibility: Any ASIC vendor can support SONiC by providing a SAI library

Standardization: Easier to add new features at control plane without touching hardware SDKs

📝 Summary
SAI is a standard API layer that abstracts hardware-specific details, allowing SONiC to work on any vendor’s ASIC using the same control-plane software.

Route Learned (Control Plane)

bgpd (FRR) receives route updates from a BGP peer.

Installs them into the Linux kernel routing table via zebra.

fpmsyncd

Monitors the FPM (Forwarding Plane Manager) channel.

Captures the new route entries and pushes them into the Redis APPL_DB.

orchagent

Watches the APPL_DB for new route entries.

Resolves the needed next-hop, interface, neighbor info.

Converts the route data into SAI object API calls (e.g. create_route_entry()).

syncd

Receives SAI calls from orchagent.

Loads the vendor’s SAI shared library (libsai.so).

Calls the vendor SAI API, which internally uses the ASIC vendor’s SDK.

The vendor SDK writes the route entry into the hardware forwarding tables (TCAM/LPM).

Packets matching this route are now forwarded entirely in hardware.
